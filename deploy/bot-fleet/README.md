# Maestrly bot fleet images

Build on the target Linux architecture with `node scripts/bot-fleet-images.mjs --platform linux/arm64 --from-head` (or `linux/amd64`). `--only bot` and `--only gateway` select one image. Transfer images with `docker save`/`docker load` if building elsewhere. The builder tags each image with the root package version and `:local`. It runs `npm ci` **inside Docker**; the macOS host installation is not reused.

## VPS setup

Install Docker Engine and Tailscale on the VPS. Build or load both images, copy `.env.example` to `.env`, set the image tags and time zone, then run `docker compose -f deploy/bot-fleet/compose.yml --env-file deploy/bot-fleet/.env up -d`. Expose only the loopback gateway through the tailnet, for example `tailscale serve --bg https / http://127.0.0.1:7443` (check the syntax for your installed Tailscale version). Pair with `docker compose -f deploy/bot-fleet/compose.yml exec maestrly-bot-gateway node apps/bot-gateway/dist/main.js pair`.

The gateway joins the fixed `maestrly-bots` Docker network and can create bot containers there. It starts as root only long enough to map the mounted Docker socket's numeric group ID into the `node` user's supplementary groups, then runs Node as that user. The mounted socket gives the gateway effective root access to the Docker host. Host root can read the gateway database, bot home volumes, tokens, and encrypted keyring material. Keep the VPS and backups private. Do not publish port 7444, 7680, 5900, or 5901. The VNC servers deliberately have no password: only the fleet network may reach them, and access control belongs to the gateway.

## Bot container contract

The image runs the Linux `electron-vite` build from this repository under the Electron binary installed by the workspace. This is an unpackaged development form: `app.isPackaged` is false. The official, version-pinned Codex and Copilot runtimes and Cursor helper are materialized for the target architecture during the image build. The tunnel client is also materialized. Local ML is **not** bundled, so its features are unavailable until that runtime is installed through an adapted flow. Provider authentication and actual requests require live accounts and have not been verified by this image build. The packaged release form was not used because the current release wrapper requires the local ML archive and runs its packaging gates. Both forms use this repository's desktop source.

Create bot containers with `Init: true`, `ShmSize: 1073741824`, an isolated home volume at `/home/bot`, user 1000 (the image default), no published ports, and the fleet network. Set all §6.3 bot env vars including control/gateway tokens and `MAESTRLY_BOT_KEYRING_PASSWORD`. Use a random, stable password per bot, stored in the gateway's private data. The entrypoint unlocks GNOME Keyring on a private D-Bus session; Electron uses `--password-store=gnome-libsecret`. This keeps `safeStorage` encrypted but the password is present in Docker container metadata and readable to host root. Rotating it requires coordinated keyring migration. `--password-store=basic` is not an acceptable substitute for encrypted credentials.

The session uses Xvfb, Openbox, tint2, and two `x11vnc` servers. Port 5900 accepts input; 5901 uses `-viewonly`. Both use `-nocursorshape -nocursorpos -noxfixes`, baking a generic arrow into framebuffer updates so a passive viewer can see xdotool pointer motion. Dynamic cursor shapes are not retained; the raw RFB frame probe detects the arrow moving. The `openbox-rc.xml` declares its mouse and keyboard bindings explicitly because `--config-file` replaces defaults. `xdg-open` routes web links to the Debian `chromium` package. Docker's default seccomp profile blocked Electron's namespace setup in the local Linux/arm64 OrbStack VM on macOS. The shipped `seccomp-bot.json` starts from Moby v26.1.5's default profile and additionally permits `clone`, `clone3`, `unshare`, and `setns`. The gateway image embeds that profile; gateway config expands `MAESTRLY_GATEWAY_BOT_SECURITY_OPT=auto` into the Engine API value `JSON.stringify(["seccomp=" + JSON.stringify(profile)])`. A manually supplied JSON array bypasses this default. The exact Engine API `SecurityOpt` array has one string containing `seccomp=` followed by the compact JSON profile. This worked on the local OrbStack Linux/arm64 VM. Docker Desktop and stock Linux Engine with AppArmor have not been tested. Ubuntu 24.04's AppArmor user-namespace restrictions are one reason to use Debian 12 here. `--no-sandbox` is not passed. The desktop source currently configures its main renderer with `sandbox: false`; the desktop implementer must revisit that preference to sandbox the renderer itself.

The bot healthcheck calls `/v1/health` with the bearer token and fleet protocol header. On committed `HEAD`, bot mode is not yet present, so that healthcheck is expected to fail. The gateway `serve` command is also a scaffold on `HEAD`; its `/v1/meta` healthcheck can only pass after the parallel gateway implementation lands.
